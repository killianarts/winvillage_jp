# Reservation Form

So far, I have a working-but-incomplete reservation form, complete
with payments. The reservation form is a multi-step form built with
HTMX and payments are done through Square.

# The Road Thus Far

I first work on trying to build a calendar. When customers make a
reservation, they need an interface that communicates clearly and that
is easy to use. Influenced by the airplane ticket process that I went
through to come to the US, I envisioned two calendars side-by-side,
allowing customers to select a 'range' of dates for their reservation.
With that in mind, I began working on learning how to build calendars
with Python's `calendar` and `datetime` libraries.

I quickly realized that making a calendar was more challenging than I
had at first imagined. Thus, I decided to look for other projects that
had implemented some sort of custom calendar feature.

I found four different "scheduling" or reservation libraries for Django:
django-schedule, django-scheduler, django-reservations, and another one,
can't remember the name.

`django-schedule` appears to be the base for the other two libraries. I
liked that it used Python's `calendar` library, meaning I could create
calendars on the backend in my templates and then render and manipulate
them with HTMX and _hyperscript. However, it was an older library and
also appeared to not be the precise fit for what I wanted to do. The
same was true of the other two forks of `django-schedule`.

`django-reservations` seemed closer, but was poorly documented (all of
these libraries were, to be fair) and seemed to have a different
use-case than mine.

## Mistake: Overcomplicating things

After reading the code for these different packages, I decided to take
some of the code from the `django-reservations` library and build my
application based on the bits I took from it. That was good because I gave
up on trying to use some outside library for the calendar (temporarily,
at least) and could focus on getting to work on the meat and potatoes
of the rest of the process.

Unfortunately, borrowing that code was a mistake.

### Reason #1: Didn't understand purpose of the code

One reason it was a mistake is because I didn't fully understand what
the full purpose of the code was. The meat of the code was a Django
model that implemented a Generic Foreign Key field. I didn't (and still
don't) understand fully what the value of a generic foreign key field
is, but it seemed to allow some extra flexibility over a simple foreign
key to another specific model.

### Reason #2: Difficult to understand and use

While building the form, using the reservation model was cumbersome and
difficult to reason about. Because I got stuck on trying to use the
Reservation model 'correctly', I didn't see how it was negatively
effecting other design decisions I was making.

### Reason #3: Bad code design decisions influenced by borrowed code

To build up the form for final submission, I tried saving data to a
session. I wasn't saving any data in the database until the end of the
process. That made my life more difficult for various reasons. The
decision to build up in session data was partially influenced by my
borrowed Reservation model.

## Resolution: Throw Away Complex Code

After I limped along and got to the final stage of the form, it was
becoming obvious that I was going down a bad path. I reflected and
decided to borrow code I had previously borrowed and used successfully
to build a shopping cart for an ecommerce site demo I was working on.

Throwing away the complex code allowed me to see more clearly how I
could simplify the process by saving data to the database at every step
of the process and simply recall the data at every step.

## Mistake: Not Enough Planning

Another mistake I made was trying to implement behavior without fully
thinking through the implications or how the form should look to the user.

At one step of the form, users can decide what kinds of 'options' to
add to their reservation. Do they want to buy a grill? Do they want to
buy some food?

The first implementation of this feature involved a simple Boolean form
field. `Buy Grill? ($200)`

### Reason #1: Bad User Interface

It was a simple solution, but it had two downsides. The user interface
was a bit too simple, and I needed to figure out what to do `if
buy_grill == True` at the very end of the process.

Leaving the user interface too simple, along with the
build-up-data-in-session design decision, strangely had the effect of
making the process more complicated to code and reason about.

### Reason #2: No Planning

Because I didn't plan exactly how the process should look to the user,
I didn't have a clear idea of how to design the code to fit the problem.
Of course, this was partially related to the session decision I talked
about before. However, because I postponed making hard decisions until I
had coded all previous steps and finally made it to the final step of
the reservation process, I had many design decisions to make all at once.
Of course, if I had planned everything ahead of time, I would still
have needed to make those hard decisions all-at-once, but at least I
wouldn't have spent days banging my head on my keyboard and asking
JetBrains AI assistant to help me understand what the hell was going on.

## Resolution: Reframe Problem and Build Idea Out More Before Coding

To solve both problems, I reframed the `options` step as "adding or
removing items from a cart". Doing so cleared the fog and helped me
design better code and better UI.

I used a simple `Items` model, made a `grill` item or two, and then
call those items from the database. I used HTMX and separate `add-item/`
and`remove-item/`endpoints to run those operations on each of those
items and update the items' state on the front end. Simple, elegant,
beautiful.

Doing so not only improved the `options` step, it also made the final
step more obvious. I needed to show the customer what the bill would be
and give a price breakdown for each item, just like you would in a
checkout process for an ecomm site.
